# sqlib comprehensive review

Reviewed at commit a6f2218 (main). Method: build, typecheck and full test run on this tree (all green: 3839 API tests in 124s, plus srl 211, rdf-delta 264, runtime 146, runtime-oxigraph 13, tools 20, mcp-server 14), then six parallel in-depth reviews (persistence/cache, routes/auth, execution engine, web SPA, library packages + MCP, tests/CI/docs). Every finding below was verified by reading the code; the top ones were re-verified by hand.

Scale: api 65K src / 84K test lines, web 117K src (excluding ui primitives) / 40K test, seven smaller packages ~25K. 52 entity types, 24 route files, 19 feature flags, 89 MCP tools. Repo history here is 10 days old; 79 of 156 commits are Claude co-authored.

## Part 1 — Ranked findings

### CRITICAL / HIGH: security and authorization

**S1. Caller-supplied `id` on create overwrites any existing entity, including one in another library.**
`routes/queries.ts:107` (`const id = body.id || mintId('query')`), same in `query-groups.ts:158`, `tags.ts:145`, `tuple-sets.ts:396`. `CacheCoordinator.create` (`lib/CacheCoordinator.ts:267-295`) never checks existence; the insert is additive `INSERT DATA` and `setInCache` re-points `_idToType`. The entity guard only checks `write` on the body's `isPartOf`. `libraries.ts:491` fixed exactly this for libraries (409 with a comment explaining the takeover) and the fix was not propagated. Escalation: POST a Query with `id = <library IRI>` re-types the library in `_idToType`, after which `resolveOwningLibrary` returns null for every entity in it and the guard abstains.
Fix: reject in `CacheCoordinator.create` when the id exists (one change, closes five routes) and add a test per create route mirroring `libraryRoutes.test.ts`.

**S2. Test runs and benchmark runs execute under the server's identity; backend grants are never checked.**
`lib/TestRunner.ts:221` and `lib/BenchmarkRunner.ts:258` default to `new ExecutorFactory()` with no scope; `routes/tests.ts:1063,1171` and `routes/benchmarks.ts:30` construct them that way; both also build a bare `new ExecutionEngine()` for group subjects. `auth/executionScope.ts:37` short-circuits on absent scope. `POST /tests` never checks the caller may execute the subject's library. Benchmarks have no `isPartOf`, so the guard abstains on every benchmark route, and `test/auth/route-matrix.test.ts:242-245` pins `UNGUARDED: stranger runs a benchmark → 200`. A caller with execute+write on one library can run any saved UPDATE query against any backend (including the library store) with server credentials. This contradicts architecture.md step 5 and security-model.md's "Tier 1 ships".
Fix: thread `{ request, viaLibrary }` into both runners and the engines they create (as `EtlService.executeEtlJob` already does); `requireLibraryMode(subjectLibrary,'execute')` + `requireBackendMode(backend,'use')` on test create; give benchmarks an owner.

**S3. Stored ETL SQL runs under an ordinary library grant.**
`routes/etl-jobs.ts:233-281` (create version with `sql`, guard `write`) and `:532-606` (execute, guard `execute`); `EtlService.executeEtlJob` has no `requireAdmin`. security-model.md says both SQL-taking routes need admin under `required`; only `/etl-jobs/preview` and `/playground/etl/execute` do (`sqlRoutesAdminOnly.test.ts`). Also `tuple-sets/from-etl` → `lib/tupleSetFromEtl.ts:142`.

**S4. Read-only bypass and update-over-GET on `/sparql`.**
`routes/sparql.ts:277` guards `record=patch` in POST only; the GET handler (`:408-476`) computes `recordPatch` and persists a Patch entity, and `config/readOnly.ts:35` only intercepts POST/PUT/PATCH/DELETE. `GET /sparql` also executes UPDATEs (`:476`). Combined with S5, that is CSRF-able.

**S5. CORS `origin: "*"` with `credentials: true`** (`index.ts:701`, comment "During development, allow all origins") on a server whose default auth mode is `disabled`. Same in `mcp-server/src/http-server.ts:43-44`, which reflects the request origin with credentials.

**S6. Cross-library reads without a read check.** `ArgumentSetService.exportRuntimePayload` in `/execute` and `/sparql` takes ids only (`routes/execute.ts:430`); `RuleSetVersionWriter.ts:49-78` accepts any RuleVersion/DataBlockVersion (query groups fixed this in issue #489, rule sets were not); moving an entity via `isPartOf` on PUT checks the source library but never the destination (`queries.ts:142`; rules/data-blocks/data-graphs/tests have zero explicit checks); `query-groups.ts:298-440` version routes have the dangling-parent gap that `queries.ts:213-228` documents and fixes.

**S7. DynamicQueryNode resolves any QueryVersion in the process** with no library, read, or query-type check (`orchestration/ExecutionEngine.ts:1361-1414`). An UPDATE version from another library can run against the node's backend; `refuseUnroutedArguments` disables itself when a dynamic node is present (`:925-927`).

**S8. MCP HTTP transport.** `mcp-server/src/http-server.ts:97-104`: any POST with a missing/stale/forged `mcp-session-id` creates a fresh Server+transport; non-initialize bodies get 400 (should be 404) and the object is never registered or closed, so it leaks. Sessions are not bound to the caller's token, so anyone holding an id can attach to, post into, or DELETE another caller's session. `addContentTypeParser('*')` on the shared Fastify instance changes REST content-type behaviour in `dual-http` mode. Zero tests for the transport.

**S9. Token verification edges** (`auth/tokenVerifier.ts:280-295`, `auth/config.ts:412`): audience validation is skipped when `SQLIB_AUTH_AUDIENCE` is unset, so any token from the issuer for any app is accepted; `ERR_JWKS_NO_MATCHING_KEY` maps to 503 (server-blamed, triggers JWKS refetch); public-path matching uses `endsWith('/health')` / `includes('/docs/')` on the raw URL rather than the route pattern.

### CRITICAL / HIGH: correctness

**C1. Clearing a field to `null` never reaches the store.**
`lib/CacheCoordinator.ts:326`: `patchRecord[key] = value === null ? undefined : value`; `persistence/writeQueryGenerator.ts:82` treats `undefined` as "not patched". The cache merges the original `null` (`:346`), so cache and store diverge and the old value resurrects on the next TTL refresh. Exercised today by backend delete (`routes/backends.ts:1027,1036` sets `defaultBackend: null` on libraries and queries). Generator test passes because it tests the generator alone. One-line fix plus a coordinator-level test.

**C2. Background SWR refresh overwrites concurrent writes.** Type refresh (`CacheCoordinator.ts:442-460`) snapshots `findAll`, then deletes every cached entity of the type and replaces with the snapshot; a create/update that commits during the await is wiped. Per-id path (`:405-416`) same shape. No write epoch (the pattern exists in `OxigraphStoreManager.memoryEpochs` but is not applied here). The doc promise "your own writes are visible immediately" does not hold under a concurrent refresh.

**C3. Version numbering and `currentVersion` are unsynchronised read-then-write**, in five separate implementations (`versionNumbering.ts`, `QueryVersionWriter.ts:125`, `RuleSetVersionWriter.ts:88`, `GroupVersionWriter.ts:563`, `BenchmarkExperimentService.ts:199`). Concurrent saves mint duplicate numbers; with `CACHE_PRELOAD=false` numbering restarts at 1. Three writers discard the result of the pointer flip while others throw on null.

**C4. `oxigraph-memory` is not ephemeral.** `orchestration/ExecutorFactory.ts:261-270` calls `createPersistentStore(..., { storeType: 'persistent' })`, which restores from and serialises to `./storage/oxigraph/…memory.nq` on shutdown. The docs hedge ("read the code before relying on it"); the code should be fixed.

**C5. Ephemeral execution stores are keyed by an author-chosen persisted string.** `GraphBuilder.ts:159-176` passes `storeId` verbatim; `OxigraphStoreManager.createEphemeralStore` returns an existing store with that id. Two concurrent runs of the same group share one store; whichever finishes first destroys it (`ExecutionEngine.ts:420-422`) and the other's `materializeRdfResult` silently warns and returns (`:1319-1323`). The ExecutorFactory comment claims per-execution isolation that the code does not implement. Fix: namespace by run id.

**C6. `stratify()` compares terms by prefix+local text** (`srl/src/stratify.ts:337`), so `ex:q` in a head and `<http://example.org/q>` in a body never match. Verified by running: a negative cycle is reported stratifiable without `expandIris`. Two callers skip expansion: the package's own W3C harness (`test/w3c.harness.test.ts:51,68`) and the API conformance path (`api/src/lib/srlChecks.ts:82`, used by `TestRunner.ts:439`). Production paths do expand.

**C7. Web: the SSE change feed only refreshes queries.** `web/src/composables/useLibraryRefresh.ts:38-56` is hard-wired to `queriesStore`; the API emits `changed` for 12 entity kinds (`api/src/lib/changeEvents.ts:134-147`). An MCP edit to a rule set fires `GET /queries/<ruleSetId>` (404, swallowed) and the rule-set editor stays stale with a stale ETag.

**C8. Web: hand-rolled `testCaseSchema` strips `dataGraphs`.** `useApiClient.ts:416-431` has no `dataGraphs` field (API returns it, `routes/tests.ts:98`); TestWorkArea never reads or writes it. Re-saving a multi-graph test from the UI mints a new version with the graphs gone.

**C9. Engine: a SELECT→VALUES hop aborts when any upstream row has all mapped columns unbound** (`ExecutionEngine.ts:717-733` produces `{}`, which `parser.ts:615` refuses as a wildcard mixed with bound rows). Legitimate OPTIONAL output kills the run.

**C10. Engine: RDF hand-offs disagree on format.** CONSTRUCT nodes honour the request `Accept` (`ExecutionEngine.ts:288`), but RuleSetNode seeding passes no `initialGraphFormat` (`:164-166`, default `ntriples` at `RuleSetExecutor.ts:299`) and EndNode fan-in does `rdfOutputs.join('\n')` assuming N-Triples (`:396-401`). `Accept: text/turtle` breaks a group with a rule set node.

**C11. No timeouts or cancellation in group/rule execution.** `oxigraph.Store.query()` is synchronous and blocks the event loop; `ExecutionEngine.execute` takes no AbortSignal or deadline; the rule "timeout" is measured after the fact (`RuleSetExecutor.ts:882-887`); benchmark's `setTimeout` race is never cleared and cannot stop the task. Only DuckDB has real cancellation.

**C12. Web drafts in `localStorage` with no size cap, try/catch, or cross-tab sync** (`useCallableDrafts.ts:257-263`). DataGraph and TupleSet work areas write whole documents every 500ms; a `QuotaExceededError` inside the debounce silently stops all draft persistence for every section. `lib/lastRunCache.ts` shows the same author knew the hazard.

**C13. `update()` reports success when the store did nothing** (`CacheCoordinator.ts:307-347`): a cache-only entity gets a no-op DELETE/INSERT/WHERE, `fresh` is null, and the merged entity is returned as persisted with a bumped ETag. A type that fails to load at boot has zero entries and therefore never triggers a type refresh (`:424-427`), so it stays empty until restart while `/health` says ready.

**C14. Runtime bundle "integrity" hashes only `template.text`** (`runtime/src/bundle.ts:482-490`); slots, prefixes, pageParameters are unhashed and prefix rows unvalidated. An edited prefix namespace silently produces wrong IRIs with a valid hash. Docs say it "catches any edit".

**C15. `require('stream')` in an ESM module** on the Oxigraph streaming path (`server/OxigraphSparqlExecutor.ts:116,146`), reachable via `SystemQueryRunner` graph-typed queries under the in-process backend.

### MEDIUM: conceptual and structural smells

**D1. Versioned-entity CRUD is hand-written seven to nine times with measured drift.** Across `routes/*`: 20 `validateIfMatch` sites, 18 `findVersionByNumber`, 16 `analyseReferences`, 81 `setEntityConcurrencyHeaders`, 43 bare 404s, 14 "must belong to exactly one library" in 3 wordings. Drift already present: `/v` vs `/versions`; DELETE returns 204/404/409 and cascades or not depending on module; version PATCH honours If-Match only in queries; `ImmutableEntityError` maps to 400 in rules and 409 elsewhere; version create failure is 500 in queries and 400-for-anything in rules/data-blocks/data-graphs; explicit auth checks present in queries/tuple-sets/libraries and absent in rules/data-blocks/data-graphs/tests. `route-helpers.ts` has two verbatim copies of the same 60-line error wrapper (`:147-210`, `:295-353`) and `index.ts` a third. Every security fix in this review that was applied to one module and not its siblings (S1, S6) is this smell made concrete. A `registerVersionedEntityRoutes(...)` would replace ~3,000 lines and the drift table is its acceptance test.

**D2. The same shape in the web: 8 WorkAreas reimplement load→draft→save-version→run.** `persistDraft` ×8 (each stuffing a query-shaped `CallableDraft` with `type:'query'`, `resultKind:'BOOLEAN'` for a test), the identical 500ms debounce watcher ×7, `hydratingRecord`/`matchesSaved`/`discardDraft`/`locallySavedAt` ×8, `deriveIfMatchToken` copied into 6 stores. `lib/entityLifecycle.ts` declares "One model, every section" and is imported by two files. C7, C8, C12 are consequences.

**D3. `useApiClient.ts` (3,421 lines) is a hand-written client with 169 closures and 20 local zod schemas** that duplicate what `@sparql-query-lib/contracts` generates; `routes.generated.ts` is imported by zero web files; ~49 `as never` casts at write sites disable the compiler on the wire. `src/types/*` is a second parallel type world (46 importers vs 50 for contracts). The contracts package exists precisely to prevent C8 and does not, because the web does not use it for these shapes.

**D4. Three copies of "invoke a callable" in the API** (TestRunner, BenchmarkRunner, ExecutionEngine node branch) each doing applyLimitOffset→applyArguments→switch(queryType)→executor; both runners build fake `ResolvedNode`s to reach `getExecutorForNode`. `resolveInput/OutputTupleNames` duplicated between engine and GraphBuilder with different error behaviour. Two `convertRowsToBindings` (engine vs EtlService) already disagree: one `encodeURIComponent`s IRI template values and skips bad rows, the other does not, so the same ETL job yields different IRIs as a group node vs run directly. `ExecutionEngine.execute` is ~330 lines with the Kahn indegree-advance block pasted five times.

**D5. `pages/index.vue` (2,413 lines) is a hand-rolled router**: ten WorkAreas in a `v-else-if` chain keyed per section (so switching unmounts a 3K-line component), 13 `selected*Id` refs, 9 hand-parsed query params, 41 per-entity `handle*Saved/Deleted` handlers. No Pinia, no provide/inject; the module-singleton composable pattern is consistent and fine, but the page is the integration point instead of a route tree.

**D6. LIMIT/OFFSET parameters are regex-on-text, not AST** (`runtime/src/limit-offset.ts:110-123`, `parser.ts:283-296`). Placeholders inside comments or string literals are detected as parameters and rewritten; `formatQueryString`'s sentinel dance exists to survive this. architecture.md step 6 says "never on the query text". Injection is closed by integer validation; this is spec fidelity.

**D7. Two persistence disciplines.** Six benchmark types and TestRun/TestRunCase are written directly through lenses (`EntityStore.ts:9-15`, `TestRunStore.ts:169-182`) and are neither cached, immutability-guarded, nor on the change feed. The LDKit migration is functionally complete but not finished: `LENS_BY_TYPE` imports ~50 `*Utils` modules for a map whose keys already exist in `entityTypeNames.ts`; `getLensForType`/`CommonLens` have no production callers; `EntityAssembler.ts:5` and `EntitySerialiser.ts:17` cite `readParity.test.ts` / `createParity` as their spec and neither file exists; names `LdkitQuery`, `toLdkit`, `ldkit:IRI` persist.

**D8. Dates are `Date` objects or ISO strings depending on which path wrote the entity** (`EntityAssembler.ts:32-40` vs `CacheCoordinator.create:281`), interfaces say `string`, and `route-helpers.ts:121-135` branches on `typeof` at runtime.

**D9. Immutability is keyed on a stored flag, not the type** (`lib/immutability.ts:39`), covers 8 of 12 version types, and `create()` has no guard, so a re-create of an existing version id (S1) rewrites a frozen snapshot.

**D10. `rdf-delta` has outgrown its stated boundary**: architecture.md says pure derivation, no fs/network; `src/index.ts:40-101` also exports an Azure/S3 blob store over `fetch`, snapshot/checkpoint/rebase, and DuckDB patch-log SQL; `poc/` is built as part of `build`.

**D11. `contracts`: hand-written modules live in `src/generated/`** (`query-version.ts`, `query-group-version.ts`, `ruleset-version.ts` say "deliberately hand-written"); `generated/sparql.ts` claims to be auto-generated and no generator writes it; `schema/contract-routes.ts` (79KB) is a hand-edited snapshot beside `routes.generated.ts` (118KB) that `schema/index.ts:17-20` admits "disagree". `test/scripts/route-generation.snapshot.test.ts` overwrites committed generated files during a test run and asserts only `length > 0`; no CI step does `generate-schemas && git diff --exit-code`.

**D12. Runtime public surface is 142 exports at 0.1.0**, including internals (`renderValuesBlock`, `alignArgumentSets`, `substituteLimitOffset`, `hashTemplateText`), `QueryHandle.exported` hands out the mutable `ExportedQuery`, `TermValue.type` collapses to `string`, and the injection test suite (`parser.injection.test.ts`) lives in the private `api` package (`sparql-terms.ts:18` cites a `sparql-terms.security.test.ts` that does not exist). `types` declares `typed-literal`/`bnode` that the runtime throws on (Virtuoso emits `typed-literal`).

**D13. Resource knobs exposed to any caller**: `rules.ts:459` `destroyStore:false` leaks an Oxigraph store per call; `maxIterations` has no maximum; `execute.ts:1127` logs full request bodies (argument values) at info; each group hop buffers whole result sets; the in-group ETL node ignores `maxRows`/streaming that `EtlService.runPipeline` was written to provide; `RuleSetExecutor` hashes the entire dataset after every rule of every iteration and returns full quad diffs per rule per iteration.

**D14. Feature-flag gating inconsistencies**: `/sparql` and `/detect-*` always registered even with `FEATURE_QUERIES=false`; `/playground/etl/execute` registered when ETL playground is off (404s inside the handler); argument sets gate on `queries||queryGroups` but tests can be on with argument sets off.

## Part 2 — The five conceptual issues underneath

1. **"By construction" claims that are not.** The codebase's best design idea is invariants that hold structurally: one scoped ExecutorFactory, one plugin-scoped guard, one generator for schemas, one change-feed hook. Each is real on its main path and has a side door built beside it (unscoped runners, guard abstaining on benchmarks and on the id-takeover, a hand-edited route snapshot, a feed the web only half-consumes). The comments describe the invariant; the code has it in one place. Reviewing every "by construction" comment against its actual callers is the highest-value pass you can do.

2. **Copy-per-entity is the root cause of most drift.** Seven route modules, eight WorkAreas, six stores, three invocation paths, five version-number implementations. Every "fixed in one module, not the siblings" finding (S1, S6, C3) is this. A generic versioned-entity router on the API and a `useEntityDraft` + store factory on the web are the two refactors with the highest payoff, and the drift tables above are their acceptance tests.

3. **The cache is a second source of truth, not a cache.** Reads are cache-only, writes are cache-authoritative on failure (C13), refresh is delete-and-replace (C2), null is lost in translation (C1). Either give it write epochs and make store failure a failure, or accept it is the truth and make the store a write-behind log. Right now it is neither, and the docs promise properties it does not have.

4. **The contracts package is not the contract.** The web re-declares shapes, casts with `as never`, and hand-mirrors constants; the API's route snapshot is hand-edited; the MCP catalogue is the only consumer that uses the generated routes as intended. Generate the web client from `routes.generated.ts` and delete the local schemas.

5. **Scope vs maturity.** 19 feature flags, 52 entity types, queries + groups + rules + tests + benchmarks + ETL + patches + assistant + notebooks + static export + MCP, on a pre-1.0 codebase whose core cache and auth layers have the issues above. The flags and off-by-default gates are the right instinct; consider whether benchmarks, ETL, patches/blob-store and notebooks should be frozen until the core (S1-S6, C1-C5) is closed.
